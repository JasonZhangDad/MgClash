# V0.1 acceptance runbook

The authority for what must pass is **PRD section 50** and the V1.1 addendum's
Phase 3 scope change; this file only says *how* to run each item and *what
counts as a pass*. Where the two disagree, V1.1 wins, as CLAUDE.md states.

Nothing here can run in CI. Every item needs a real machine, a real network, or
a real Core binary — that is why the automated suites all pass while none of
this is signed off.

## Before starting

Acceptance needs four things this repository deliberately does not contain:

| Needed | Why it is missing |
| --- | --- |
| A sing-box binary and its official SHA-256 | Release artifacts do not bundle a Core (ADR 0003) |
| An Xray binary | `release.yml` pins Xray 26.3.27 and its four official archive digests, taken from the `.dgst` files XTLS publishes |
| Real proxy servers for all five protocols | Public end-to-end paths cannot be faked |
| A Windows and a Linux machine | TUN and the platform proxies cannot be exercised from macOS |

Set these before anything else:

```sh
export MAGIES_SING_BOX_BIN=/path/to/sing-box
export MAGIES_SING_BOX_SHA256=<official digest>
export MAGIES_XRAY_BIN=/path/to/xray
export MAGIES_XRAY_SHA256=<official digest>
```

## 0. Run what the machine can already check

These are automated but excluded from CI. Run them first — a failure here means
the manual items below will fail for a reason that is already understood.

```sh
# the whole Xray config pipeline; all 8 passed against Xray 26.3.27 on
# macos-x86_64, so a failure here means something changed
MAGIES_XRAY_BIN=$MAGIES_XRAY_BIN cargo test -p magies-profiles \
    --test xray_runtime_smoke --test xray_outbound_smoke -- --ignored --nocapture

# sing-box config generation against the real binary
cargo test -p magies-profiles --test sing_box_outbound_smoke -- --ignored --nocapture
cargo test -p magies-profiles --test sing_box_runtime_e2e -- --ignored --nocapture
cargo test -p magies-profiles --test tun_smoke --test dns_smoke -- --ignored --nocapture

# the host's real System Proxy and default route
MAGIES_MACOS_NETWORK_SERVICE="Wi-Fi" \
    cargo test -p magies-platform --test macos_system_proxy_real -- --ignored --nocapture
cargo test -p magies-platform --test network_path -- --ignored --nocapture

# the OS credential store
cargo test -p magies-storage --test secret_store \
    platform_store_obeys_secret_store_contract -- --ignored
```

Start with `official_xray_accepts_every_routing_matcher_and_dns_kind`. It puts
all nine routing matchers and all four DNS server kinds into one document, so a
schema mistake anywhere in the Xray series surfaces there rather than during a
protocol test.

## 1. Install and first launch — all four targets

Per PRD 50, on macOS x86_64, macOS aarch64, Windows x86_64, and Ubuntu 22.04+:

1. Download the artifact and verify it against its `.sha256` sidecar.
2. Launch. **Expect an unsigned-build warning** — Gatekeeper, SmartScreen, or
   the absence of a repository signature. Record exactly what the user sees;
   this is the first-run experience, not a defect.
3. Confirm the platform summary names the right artifact and the right TUN
   availability: unavailable on macOS, requires-elevation on Windows and Linux.

**Pass:** the app starts and reports the correct platform on all four.

## 2. Core start and stop

| Item | How |
| --- | --- |
| sing-box starts and stops | Connect, then disconnect; the log panel shows the Core's own lines |
| Xray starts and stops | Set Core to `xray` in settings, repeat |

**Pass:** both Cores start, serve traffic, and leave no process behind after
disconnect. Check with `ps` / Task Manager.

**Verified as far as configuration goes:** every generated document is accepted
by Xray 26.3.27. What has *not* been checked is Xray carrying real traffic —
`xray run -test` validates a config, it does not prove the tunnel works.

## 3. The five protocols, end to end

VLESS, VMess, Trojan, Shadowsocks, Hysteria2 — each against a real public
server, on at least one platform, through System Proxy.

**Pass:** traffic reaches the internet through the node and the reported egress
address is the server's.

Hysteria2 must be run on sing-box. The capability matrix says Xray has no such
outbound, and the smoke test confirmed it: Xray 26.3.27 rejects a hysteria2
outbound.

## 4. Import paths

- a single share link
- a multi-line clipboard paste
- a `.txt` file through the file picker
- a subscription URL, then a manual refresh

**Pass:** every path produces usable nodes; re-importing the same list adds
nothing.

**Needs a real check on Linux:** the file picker is a WebView `<input
type="file">`, which depends on the WebKitGTK/GTK environment. CI is headless
and has never opened it.

## 5. Node management

Create manually for each of the five protocols, edit, group, reorder, delete,
run a latency test, run a URL test.

**Pass:** each operation persists across a restart, and a manually created node
connects exactly like an imported one.

## 6. System Proxy save and restore

On all three platforms:

1. Set a distinctive proxy in the OS settings by hand.
2. Connect, confirm MgClash replaced it.
3. Disconnect, confirm the original is back.
4. Connect again, then **kill the app** (`kill -9`, End Task).
5. Relaunch. **Expect the startup recovery prompt**, and confirm accepting it
   restores the original settings.

**Pass:** no leftover proxy after either a normal or an abnormal exit.

**Needs a real check on macOS beyond Wi-Fi:** service detection now follows the
default route, but only a Wi-Fi route has been exercised. Repeat step 2 on
Ethernet, a Thunderbolt bridge, and USB tethering.

## 7. TUN — Windows and Linux only

**Pass:** enabling TUN routes all traffic, disabling it restores the previous
state, and the routing table is left clean after quitting.

**Nothing here has ever run.** The development machine is macOS. Watch
specifically for:

- how elevation is requested, and what the user sees when it is refused
- whether `auto_route` and `strict_route` leave the routing table clean after an
  abnormal exit
- whether the fixed MTU of 9000 suits a real link

## 8. DNS and routing modes

Global, Rule, and Direct, each with DNS in system, plain, DoH, and DoT modes.

**Pass:** each mode routes as configured; a Rule-mode geo rule matches.

**Partly verified:** Xray accepts every routing matcher and DNS server kind the
generators emit, but accepting a config is not the same as routing correctly.
Two known differences to watch when running Rule mode on Xray:

- a domain suffix matches slightly wider than on sing-box (`domain:cn` also
  matches bare `cn`)
- `PreferIPv4` and `PreferIPv6` both become `UseIP`, so the ordering preference
  is gone

## 9. Recovery

| Item | How | Pass |
| --- | --- | --- |
| Sleep/wake | 50 cycles | No persistent loss of connectivity |
| Network switch | Wi-Fi ⇄ hotspot ⇄ Ethernet | Session recovers by itself |
| Core crash | `kill -9` the Core while connected | Bounded retry, then a clear error |

A recovery that acted is logged at `INFO`; a healthy probe deliberately logs
nothing, so an empty log during a stable period is expected, not a defect.

## 10. Measurements

From PRD section 5.1:

| Metric | Target |
| --- | --- |
| Startup success rate | ≥ 99% across the test devices |
| Connect success rate | ≥ 99% with a correctly configured node |
| Node switch | ≤ 2 s |
| Cold start to usable | ≤ 3 s |
| Idle CPU | < 2% |
| Idle memory | < 200 MB, excluding the Core |
| Continuous run | 72 hours |

The 72-hour run has a harness:

```sh
MAGIES_SOAK_CORE_BIN=$MAGIES_SING_BOX_BIN \
MAGIES_SOAK_DURATION_SECS=259200 \
    cargo test -p magies-session --test soak -- --ignored --nocapture
```

That exercises the session layer, not the packaged app. A real 72-hour run of
the built artifact is a separate item, and memory growth is the thing to watch.

## 11. Settings

Launch at login, connect on launch, close-to-tray, default log level, Core
choice, TUN.

**Pass:** each survives a restart and does what it says.

**Needs a real check on all three platforms:** the login item is created by
`tauri-plugin-autostart` and has no automated coverage. Confirm the entry
actually appears and disappears:

| Platform | Where |
| --- | --- |
| macOS | `~/Library/LaunchAgents` |
| Windows | `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` |
| Linux | `~/.config/autostart` |

## 12. Diagnostics and logs

Export a diagnostic bundle while connected. Open the log panel at each level and
with each source filter.

**Pass — and this one is a security check, not a feature check:** neither the
bundle nor the log panel may contain a credential. Search the exported file and
the panel for the node's password or UUID. Core output is redacted before it is
stored, but that redaction has only been tested against synthetic lines.

## Recording the result

PRD section 50 is a checklist of 32 items and section 51 defines Done. Record
per item: platform, build identifier, date, pass or fail, and for a failure the
exact observed behaviour. A failure that is understood and accepted still needs
writing down — spike reports in this repo end with a "Remaining work" section
naming what was *not* verified, and the acceptance record should keep that
habit.
